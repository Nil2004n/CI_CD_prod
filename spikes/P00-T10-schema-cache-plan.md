# P00-T10 — Versioned Kubernetes schema cache plan (D-11, Tech §25, FR-26)

## 1. Purpose, scope and status

**Status: plan only. Nothing has been downloaded, bundled or installed. Every decision below is a proposal; the decisions belong to the owner (section 11).**

Purpose: define how the pilot obtains, verifies, stores and uses Kubernetes JSON schemas for kubeconform without runtime network access, and how kind/apiVersion-derived paths are kept inside the cache (FR-26). The plan feeds P13 (kubeconform adapter).

Facts come only from the P00-T10 read-only lookup log (`evidence/P00/P00-T10/lookups.md`, cited as [L1]–[L11]), the P00-T09 kubeconform evidence, and the frozen interface in `spikes/P00-T10-request.md` §2. Lookup values were read through a summarising fetch tool and may lag the live pages (section 12).

Out of scope: downloading any schema, running kubeconform, changing specs or contracts.

## 5. Integrity

| Rule | Detail |
|---|---|
| Pinned revision | `origin.revision` is a 40-hex commit (or a release tag for B). Never `master`, `main` or a branch name. |
| Manifest | `manifest.json` exactly as the frozen interface: `manifest_version`, `set_id`, `origin{name,url,publisher,revision,licence}`, `kubernetes_version`, `variant`, `retrieved_at`, `files{relative path: sha256 hex}`. |
| Per-file SHA-256 | Computed by the application at retrieval time and stored in `files`. |
| Optional cross-check | During retrieval, compare against Git blob ids reported by the GitHub contents/trees API. This detects transport corruption only; it does not authenticate the publisher. |
| No signatures | GitHub provides no signatures or attestations for these sets (lookups limitation). The trust anchor is the pinned commit plus the owner's decision to accept that commit. |
| All or nothing | Any mismatch makes the **whole set unavailable**; nothing is partially trusted. |

Layout (frozen interface):

```
<cache_root>/<set_id>/manifest.json
<cache_root>/<set_id>/v<MAJOR>.<MINOR>.<PATCH>-standalone-strict/<kind>-<group0>-<version>.json   # named groups
<cache_root>/<set_id>/v<MAJOR>.<MINOR>.<PATCH>-standalone-strict/<kind>-<version>.json            # core group
```

`set_id` matches `[a-z0-9][a-z0-9._-]{0,63}` (one cache set per origin + revision + Kubernetes version).

Verification statuses of `verify_set(cache_root, set_id) -> (status, details)`:

| Status | Meaning |
|---|---|
| `available` | Manifest valid; every listed file present, regular, not a symlink, with matching SHA-256; no unlisted files |
| `unavailable_missing_manifest` | `manifest.json` absent |
| `unavailable_bad_manifest` | Manifest is not UTF-8 JSON or does not match the frozen manifest shape (details are in the returned `details`) |
| `unavailable_hash_mismatch` | A file's SHA-256 differs from the manifest |
| `unavailable_missing_file` | A listed file is absent |
| `unavailable_extra_file` | A file exists in the set that the manifest does not list |
| `unavailable_symlink` | Any symlink in the set |
| `unavailable_not_regular` | A listed path is not a regular file |

Verification runs before every scan (or per run session) and its status is shown in diagnostics.

## 6. Freshness

- The manifest `retrieved_at` (RFC 3339 UTC) and the target Kubernetes version are shown in diagnostics and in reports (Tech §25).
- `freshness(manifest, now, max_age_days)` returns `fresh`, `stale` or `unknown` (for example an absent or unparsable `retrieved_at`).
- The threshold `max_age_days` is an **owner policy input**; the prototype takes it as a parameter and no default is proposed here beyond "owner decides".
- Origin A updates daily [L1, L4]. That does **not** mean the local cache refreshes automatically: a refresh is a separate approved `schema_fetch` and produces a new set (new revision, new `set_id`).
- A stale set is reported, not silently refused; whether stale should block or only warn is an owner decision.

## 7. Network and the `schema_fetch` operation

| Operation | Network | Approval |
|---|---|---|
| `schema_fetch` (populate or refresh a cache set) | Yes, limited to the approved origin and pinned revision | Required per operation (Tech §25) |
| Scan | None: `network_policy="cache_only"` | Not applicable |

Scan-time kubeconform rules (builds on T09):

1. Always pass an explicit local `-schema-location`, a template into the verified set, for example `<cache_root>/<set_id>/{{.NormalizedKubernetesVersion}}-standalone{{.StrictSuffix}}/{{.ResourceKind}}{{.KindSuffix}}.json` (template variables per [L6]; local paths accepted [L6]).
2. Never pass the literal `default`, and never rely on a no-flag default: with no `-schema-location`, T09 observed kubeconform trying the network (`raw.githubusercontent.com`) and failing as `statusError` in a loopback-only namespace.
3. No `-cache` is needed for local locations: T09 observed that a local `-schema-location` wrote no cache files. (`-cache` only applies to HTTP-downloaded schemas [L6].)
4. Never pass `-ignore-missing-schemas` or `-skip`: they would turn a missing schema into a silent non-validation.
5. The kubeconform version in the lookup log matches the installed, hash-verified 0.8.0 [L7]; cache behaviour is "verified per pinned kubeconform version" (Tech §25).

## 8. FR-26 containment

T09 finding: a `kind` containing `../` segments **escaped the schema root** (kubeconform exit 0, `statusValid`), because kubeconform derives the schema file name from the resource's own `kind`. (T09 also saw its directory walk follow links in scanned directories, which is why explicit file operands are used for scope; that is a scope matter, separate from schema-path containment.) Therefore kind and apiVersion from scanned files are **untrusted** and the application must not rely on kubeconform to contain them.

Rules (frozen interface):

| Step | Rule |
|---|---|
| 1 Validate **before invoking kubeconform** and before any mapping | `kind` matches `^[A-Za-z][A-Za-z0-9]{0,62}$`; `apiVersion` matches `^(?:[a-z0-9](?:[a-z0-9-]{0,61}[a-z0-9])?(?:\.[a-z0-9](?:[a-z0-9-]{0,61}[a-z0-9])?)*/)?v[0-9]+(?:(?:alpha|beta)[0-9]+)?$`. Otherwise `invalid_identifier`. |
| 2 Map name | `kind` lowercased; for `group/version` the suffix is `-<first DNS label of group>-<version>`; for core `v1` the suffix is `-v1`. Example: `Deployment`, `apps/v1` -> `deployment-apps-v1.json` (as observed in T09). |
| 3 Contain | The mapped path is joined under the version directory and resolved. It must stay inside `<cache_root>/<set_id>/`, no component may be a symlink, and the file must be a regular file. |
| 4 Violation | Otherwise `containment_violation`, and the cache set is treated as unavailable. |

Application behaviour: the application parses the selected files itself, runs `lookup` for each resource, and only resources with status `found` are given to kubeconform. Resources with `invalid_identifier` are reported as unsupported (never passed). A `containment_violation` aborts validation for that set and is shown as an incident, not a pass.

## 9. Missing CRD or kind

| Situation | Status | Result |
|---|---|---|
| Valid identifiers, no schema file in the set | `unsupported_missing_schema` | A **gap**, reported as unsupported/incomplete (PRD SCAN-03), never `passed` |
| Invalid kind/apiVersion | `invalid_identifier` | Reported as unsupported, never `passed` |
| Set failed verification | `set_unavailable` | All resources unsupported for that set; reason shown from `verify_set` |
| Path escapes the set, symlink or non-regular file | `containment_violation` | Set unavailable |

User-supplied CRD schemas are **local inputs** (SCAN-03): the application records the SHA-256 digest and path of each supplied file in the run evidence; they are separate from a verified cache set and never silently merged into it. Optional origin C, if the owner approves it, is a separate user-populated, pinned and hashed set.

## 10. Reference prototype

`spikes/t10-cache/cache.py` and `spikes/t10-cache/test_cache.py` (stdlib only, synthetic data only, written by W2 in parallel) implement the frozen interface. Function names:

| Function | Role |
|---|---|
| `validate_identifiers` | kind/apiVersion regex validation (`invalid_identifier`) |
| `schema_filename` | name mapping |
| `load_manifest` | read and validate `manifest.json` |
| `verify_set` | whole-set verification, statuses of section 5 |
| `lookup` | `lookup(cache_root, set_id, kind, api_version) -> (status, path_or_None)` |
| `freshness` | `freshness(manifest, now, max_age_days) -> "fresh" \| "stale" \| "unknown"` |

Status strings, in full.

- `verify_set`: `available`, `unavailable_missing_manifest`, `unavailable_bad_manifest`, `unavailable_hash_mismatch`, `unavailable_missing_file`, `unavailable_extra_file`, `unavailable_symlink`, `unavailable_not_regular`.
- `lookup`: `found`, `unsupported_missing_schema`, `invalid_identifier`, `containment_violation`, `set_unavailable`.
- `freshness`: `fresh`, `stale`, `unknown`.

The prototype is a specification aid for P13, not production code.

## 11. P13 hand-off and open owner decisions

**Requirements for P13:**

1. Implement `schema_fetch` as a separate, approved operation limited to the approved origin and pinned revision; it writes a new set and a manifest, never a partial one.
2. Build the manifest as in section 5; compute SHA-256 at retrieval; optional blob-id cross-check.
3. Verify the set before every scan; surface the `verify_set` status in diagnostics.
4. Validate kind/apiVersion before invoking kubeconform; use `lookup`; pass only `found` resources.
5. Invoke kubeconform with an explicit local `-schema-location` into the verified set; never `default`, `-ignore-missing-schemas` or `-skip`; scan environment carries no network permission (`network_policy="cache_only"`).
6. Classify results from parsed per-resource status, not exit codes alone; map `unsupported_missing_schema`, `invalid_identifier`, `set_unavailable` and `containment_violation` to unsupported/incomplete or incident, never pass.
7. Show `retrieved_at`, target version, revision and freshness in diagnostics and reports; record the same in `tools.json` and the check engine snapshot.
8. Record digests of user-supplied CRD schemas.
9. Port the prototype tests (traversal, symlink, non-regular, extra/missing file, hash mismatch, invalid identifiers) to the production adapter, plus the kubeconform behaviours measured in T09.

## 12. Limitations

- All external facts come from read-only lookups through a summarising fetch tool; values may lag the live pages [lookups method].
- Directory listings were over 1 MB and truncated; existence of the three target version directories was confirmed, but **per-kind files were not confirmed** [L5].
- The datreeio layout `kind_version.json` is inferred from README examples, and its contribution/automatic merge policy was not reviewed [L10].
- No signatures or attestations exist for these sets; integrity rests on a pinned commit, self-computed hashes and optional Git blob ids (lookups limitation).
- The licence conclusion for A rests on a 2-line notice [L3] versus NOASSERTION detection [L2]; no legal review was performed.
- Exact origin-A and origin-B file contents, sizes and whether the first-DNS-label rule (frozen interface) covers every group in a real set were not checked, because nothing was downloaded.
- The converter used by B has not been evaluated.
- Reference prototype tests use synthetic temporary data only; no real kubeconform run was made in T10.

## 13. Opus integration review (2026-10-24; added after integration, W1 text above unchanged)
**R-1: group collision in the frozen name mapping. Proposed fix not applied; owner decision.**
- **Cause:** the frozen interface (request §2) maps `group/version` to the suffix `-<first DNS label of group>-<version>`. Different groups that share a first label map to the same file.
- **Demonstrated** with the prototype on synthetic data (session scratchpad, not repository evidence):
  - `Deployment apps.example.com/v1` returned `found` with `deployment-apps-v1.json`, the core apps/v1 schema;
  - `Ingress networking.istio.io/v1` returned `found` with `ingress-networking-v1.json`.
- **Consequence:** a custom resource could be validated against an unrelated core schema, which risks a false `statusValid`.
- **Provenance of the rule:** it reproduces the suffix observed for kubeconform in T09 (`deployment-apps-v1.json`). Whether kubeconform's own `KindSuffix` rule has the same collision was not re-checked in T10.
- **Bounded proposal for P13 / the next interface revision:**
  - the manifest records the **full group, version and kind** per file;
  - `lookup` returns `found` only when the full group matches (for origin A, only built-in Kubernetes API groups);
  - every other group is `unsupported_missing_schema` unless a user-supplied or approved CRD schema for that exact group exists.
- **Until then:** treat any resource whose full group is not a known built-in group as unsupported.

**Integration notes:**
- Both workers' first attempts correctly stopped, because the harness creates worktrees from the default branch (`008e80c`). The retry packets added `git merge --ff-only ea50cb7` as step 0.
- The request §2 was completed with the three helper signatures that only the W2 packet had defined.
- The packet's test command (`-m unittest -v test_cache`) does not work under `-I`. Use `-m unittest discover -s . -p 'test_cache.py'`.

## 14. Owner decisions at T10 acceptance (2026-10-24)
- **R-1 is a mandatory P13 acceptance requirement (`plan.md` §5.2 FR-30).** Before production schema lookup is enabled:
  1. manifest entries identify the complete API group, version and kind;
  2. lookup matches the complete identity, never a truncated group prefix;
  3. unknown or ambiguous identities return unsupported / not assessed and never fall back to a similarly named built-in schema;
  4. regression tests include the demonstrated `apps.example.com/v1` Deployment and `networking.istio.io/v1` Ingress collisions plus valid built-in controls (`apps/v1` Deployment, `networking.k8s.io/v1` Ingress).
- **Prohibition until then:** resources of unknown or non-built-in API groups must **not** be routed through the current filename mapping (section 8 / frozen interface §2). They are unsupported / not assessed.
- **The prototype in `spikes/t10-cache/` does not fix R-1.** Its `lookup` reproduces the collision. The interface was not revised under this acceptance.
- **O-1 to O-6 remain open.** T10 acceptance approves none of the following: a schema source or Kubernetes version policy, a staleness threshold, CRD catalogue use, release bundling, or any schema download.
