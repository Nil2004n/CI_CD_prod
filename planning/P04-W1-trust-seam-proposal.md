# P04 wave 1 — trusted working directory proposal

Status: owner approved this internal direction on 2026-11-04; implementation and security verification remain pending. The approved runner amendment requires a trusted working directory, but the current `ProcessGitRunner::new(git, timeout, env)` accepts no working-directory proof, and `GitInvocation` provides no production working-directory capability. Absolute HOME and XDG paths in `GitEnv` have only syntactic checks. The process runner remains fail-closed until the listed controls are established.

Proposed internal amendment: introduce an opaque, application-created trusted-directory capability and require it when constructing a runner or a closed operation. Its constructor must reject non-absolute paths, symlink traversal, unexpected types or ownership, and directories writable by other users, and prove that a non-repository working directory is used for the version and global-configuration operations. Repository-context operations additionally require the validated checkout and held per-repository guard, with the config/layout checks specified by the Git safety annex before invocation. The implementation must spell out its directory identity revalidation, mount and same-user race limitations; path checks alone do not eliminate substitution races. The capability must not accept arbitrary argv, broaden environment inheritance, or enable file transport.

Before enabling execution, implement and locally test pinned executable trust and Git 2.53.x version refusal; exact environment and cwd; bounded concurrent input/output; timeout, process-group termination and reaping, including a helper-grandchild potency control; and fieldless, output-free errors. SSH remains fail-closed until its separate trusted configuration and known-hosts policy are verified. If the proposed proof cannot be implemented with the existing dependencies and no-unsafe rule, retain refusal and present the specific gap rather than asserting confinement.

The checkout adapter must bind its guard to the exact repository ID and confine checkout paths. Recursive deletion remains refused unless directory-relative no-follow operations can establish the approved safety boundary. Adding a dependency, changing canonical contracts, real data migration, real network access and credentials require their applicable separate approvals. The trusted-directory capability above is an internal interface proposal only; it does not resolve fixture-transport isolation or CA-06 migration.
