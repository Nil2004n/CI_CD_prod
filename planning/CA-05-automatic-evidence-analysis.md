## 1. Authoritative requirement (owner, 2026-10-31)

The application automatically analyses assessment evidence with the configured LLM as part of the normal assessment workflow. It does not wait for the user to open the RAG chat or ask for an explanation. Corrected product flow:

```text
select repositories/files
→ establish approved scope and snapshot
→ run scanners/validators
→ normalise and sanitise evidence
→ automatically perform LLM evidence analysis
→ validate and persist the structured analysis
→ produce the combined assessment/report
→ optional interactive RAG investigation
```

Automatic LLM evidence analysis is a required product capability. Interactive RAG chat is a separate, optional user interface. The requirement is newly explicit: no earlier approval, spike, test or accepted phase covered it, and historical records are not reinterpreted.

Before CA-05 the specifications described AI only as an optional chat assistant plus an optional, deferred "AI report narration" (RES-07 narration part, `GenerateReportNarrative` reserved, `AIEnrichment` in `ReportFile`, plan Q-02). CA-05 replaces the narration concept with a required automatic analysis stage and keeps chat optional.

## 3. Shared vocabulary (use these terms in every document)

| Term | Meaning | Name |
|---|---|---|
| **Scanner execution** | Running the frozen scan plan's checks; run lifecycle `queued` … `completed`/`partial`/`failed`/`cancelled`/`interrupted` | Existing `Execution` |
| **Scanner finding** (engine-confirmed) | Normalised finding produced by a scanner/validator adapter. Only scanners create findings | Existing `Finding` |

| **AI evidence coverage** | How much of the report's eligible evidence the validated analysis actually covered: `complete` (everything eligible was in the snapshot), `partial` (items excluded by budget, redaction or scope), `none` (no validated analysis) | `AnalysisFile.ai_evidence_coverage` |
| **Logical analysis** | The analysis of one report under one input configuration (idempotency key); has an `analysis_id` and an `analysis_version` per report | `AnalysisManifest`, `analysis_id` |
| **Attempt** | One execution of a logical analysis, written as one immutable record when it ends; contains up to 4 provider requests | `AnalysisFile` (`record_id`, `attempt_seq`) |
| **Authoritative analysis** | The completed attempt that represents a report's analysis (§6.2) | derived |
| **AI interpretation** | Cited analysis content that explains, relates or prioritises scanner evidence: summary, interpretations, recommendations, limitations, uncertainties | `AnalysisContent` items, origin `ai_interpretation` |
| **AI-only observation** (independent AI finding) | A claim about a problem no scanner reported, presented on its own | `observations` (reserved, empty in the pilot) |
| **Legacy AI narrative** | Content in a store 1.4 report's `ai_enrichment` | 1.4 `AIEnrichment` (§8) |
| **Interactive RAG chat** | Optional user-driven chat over retrieved redacted context | Existing chat |
| **Workflow (assessment) completion** | Whether every required stage — scanner, analysis, report — reached a successful terminal state | `AssessmentCompletion` |

Rules of language: "AI is optional" is wrong after CA-05 — "interactive chat is optional; automatic evidence analysis is a required stage". "Complete" refers to workflow stages unless qualified ("scanner coverage complete", "AI evidence coverage partial"). "Scanner-confirmed" applies only to scanner findings.

## 4. Four separate dimensions (reconciliation A)

| Dimension | Values | Answers | Never implies |
|---|---|---|---|
| Workflow completion | `in_progress`, `complete`, `incomplete` (+ `incomplete_stages`) | Did scanner, analysis and report stages all succeed? | Anything about findings or coverage |
| Scanner coverage | `complete`, `partial`, `none` | Did the selected checks run on the selected targets? | That AI saw everything; that the target is secure |
| AI evidence coverage | `complete`, `partial`, `none` | Did the validated analysis include all eligible scanner evidence? | That scanner coverage is complete; that the analysis is correct |
| Finding presence | `findings`, `no_findings`, `unknown` | Does the available scanner evidence contain findings? | That no findings means secure (always qualified by scanner coverage) |

They are stored and displayed separately. Examples: workflow `complete` + scanner coverage `partial` + AI evidence coverage `partial` + `findings`; workflow `incomplete` (analysis blocked) + scanner coverage `complete` + AI evidence coverage `none` + `no_findings`. No combined "secure" or "clean" badge exists.

## 6. Trigger, lifecycle, attempts and authority

### 6.1 Trigger and unit

- **Evidence finalisation.** A per-repository evidence report (`ReportFile` JSON) is final when its checks are terminal and the JSON is written and validated. Its digest is the analysis base.
- **Eligibility (deterministic, no model call):** explicit model configured; credential present; valid `model_transmission` grant with matching inference scope; snapshot buildable within limits; useful evidence (at least one finding, check outcome, execution failure or coverage gap with an identifiable target). Partial and failed scanner outcomes are included.
- **Trigger:** eligibility satisfied → attempt 1 starts immediately in the same run. Missing grant → `awaiting_approval`, one approval request; approval resumes the same attempt (no record is written while awaiting); denial ends the attempt `blocked`/`approval_denied`.
- **Unit:** (run, repository, report). The run summary aggregates states; no model sees two repositories.
- **Report and analysis references.** The evidence report stays AI-free and immutable. Each attempt record names `report_id` and `report_json_digest`; the run log manifest lists every logical analysis and its attempt records; each combined Markdown/PDF export records the `analysis_id`, `analysis_record_id` and version it rendered (or none). Failure handling: evidence report missing or digest mismatch → no request, `blocked`/`evidence_unavailable`; attempt record write fails → writer halts (P02 rule), attempt treated as not completed, evidence report untouched; combined export fails → evidence JSON and analysis records stay, export marked failed and regenerable without rescanning or re-analysis.

### 6.2 Logical analysis, attempts and authoritative result (reconciliation B)

- A **logical analysis** is created automatically (one per report per run) or by explicit re-analysis. Identity: `analysis_id`; per report `analysis_version` 1, 2, …; inputs fixed by the idempotency key (report digest, snapshot digest, prompt template, analysis schema, redaction version, model, routing-policy digest).
- An **attempt** (`attempt_seq` 1, 2, … within one logical analysis) is one execution; it ends in one immutable `AnalysisFile` record. Inside an attempt there are at most 4 provider requests (initial, ≤ 2 transport retries, ≤ 1 repair).
- **At most one completed attempt per logical analysis**; no attempt starts after it.
- **Automatic behaviour:** only attempt 1 starts automatically. A failed, blocked, cancelled or interrupted attempt is never retried automatically.
- **Explicit retry** (`ReanalyseReport` when the latest logical analysis has no completed attempt and its inputs are unchanged): new attempt of the same logical analysis, `trigger=explicit_retry`.
- **Explicit re-analysis** (`ReanalyseReport` when inputs changed, i.e. the analysis is stale, or the user confirms a new analysis of unchanged inputs and its possible charge): new logical analysis, `analysis_version + 1`, `supersedes_analysis_id` = previous, `trigger=explicit_reanalysis`.
- **Authoritative analysis of a report** = the completed attempt of the highest `analysis_version` that has a completed attempt. A newer version that has not completed does not erase an older completed one; the UI shows both ("re-analysis v2 failed; showing v1, stale: model changed").
- **Recovery of interrupted work:** at startup every non-terminal attempt is written as `interrupted`/`application_interrupted` with its provider requests (a request in flight is recorded as possibly billed). Pending approvals never become grants. No automatic replay; the user can retry explicitly.
- **No exactly-once claim.** The design gives at most one automatic attempt per logical analysis and refuses duplicate calls for unchanged inputs, but a request interrupted or timed out after sending may have been processed and billed. Records say so (`uncertain_generation`, `interrupted`).

### 6.3 Attempt states

```text
pending → awaiting_approval → running → validating → completed
pending → running (grant valid)          validating → running (one repair request)
any non-terminal → blocked | failed | cancelled | interrupted | not_performed
```

Non-terminal states live only in the run log manifest; every terminal attempt is written once.

### 6.4 "AI-only observations off" (reconciliation D)

Off in the pilot means: the analysis may not present an **unsupported new finding** — a problem that no scanner reported — as a confirmed or standalone assessment result. The schema's `observations` list must be empty, and the validator rejects such items (`ai_only_finding_out_of_scope`, counted).

It does **not** prohibit, and the pilot keeps: interpretations of scanner findings and check outcomes (including what a cited excerpt shows about an existing finding), prioritised recommendations tied to findings or checks, remediation and verification suggestions marked not executed, coverage limitations, and explicit uncertainty (open questions, ambiguous evidence, missing context). Every such item cites snapshot items; uncertainty items may have no citation only when they describe missing context.

## 7. Failure, limit and approval behaviour

| Condition | Attempt status / reason | Scanner evidence | Retry |
|---|---|---|---|
| No provider/model configured | `blocked` / `no_provider_configured` | Kept | Explicit retry after configuration |
| No credential | `blocked` / `no_credential` | Kept | Same |
| Grant missing | `awaiting_approval` | Kept | Same attempt resumes on approval |
| Approval denied | `blocked` / `approval_denied` | Kept | Explicit retry raises a new request |
| Evidence report unreadable or digest mismatch | `blocked` / `evidence_unavailable` | Kept as is | After repair of the store |
| Invalid key / credits exhausted | `blocked` / `provider_auth_failed`, `provider_credit_exhausted` | Kept | None |
| 429 / 502–504 before any body | transport retry; then `failed` / `provider_rate_limited`, `provider_unavailable` | Kept | ≤ 2 inside the attempt |
| No compliant route | `blocked` / `no_compliant_route` | Kept | None (no fallback) |
| Timeout or disconnect after sending | `failed` / `uncertain_generation` | Kept | None automatic |
| Truncated or invalid structured output | `failed` / `truncated_output`, `invalid_output` | Kept | ≤ 1 repair inside the attempt |
| Unsupported citations | items rejected and counted; `failed` / `unsupported_citations` if the summary is unsupported | Kept | Within the repair |
| AI-only finding in output | item rejected (`ai_only_finding_out_of_scope`) | Kept | — |
| Context budget overflow | optional items excluded (AI evidence coverage `partial`); `failed` / `context_budget_exceeded` if the mandatory set does not fit | Kept | None |
| Per-run request/analysis cap or reported-cost cap reached | `blocked` / `request_limit_reached`, `cost_limit_reached` | Kept | Explicit, after the limit is raised |
| User cancels | `cancelled` / `cancelled_by_user` | Kept | Explicit retry |
| Application exit/crash | `interrupted` / `application_interrupted` | Kept | Explicit retry |
| Attempt record cannot be persisted | writer halts; not completed; `failed` / `persistence_failed` in the manifest after recovery | Kept | Explicit retry |
| Insufficient evidence | `not_performed` / `insufficient_evidence` (no call) or completed with `evidence_sufficiency=insufficient` | Kept | None |

Limits, units, enforcement points and retry ownership: O-AN-2 proposal (`CA-05-decision-proposals.md` §1); not ratified.

Disclosure: BYOK means the user's own OpenRouter key, not on-device inference. The snapshot leaves the device to OpenRouter and the selected downstream provider under `data_collection=deny`, `zdr=true`, `allow_fallbacks=false`. Data categories: `redacted_findings`, `redacted_source`, `schema_documents`, `repository_metadata`, `app_metadata`. No key values are persisted.

## 8. Historical records (reconciliation C)

Readers present three distinct classes, derived at read time; nothing is stored or rewritten:

| Class | How recognised | Shown as | Counts as CA-05 analysis |
|---|---|---|---|
| Validated CA-05 analysis | A store 1.5 `AnalysisFile` attempt with `status=completed` for the report | AI analysis (version, freshness, AI evidence coverage) | Yes |
| Legacy AI narrative | A store 1.4 report whose `ai_enrichment.status = completed` | "Historical AI narrative (before CA-05; not validated under CA-05)", with its own model metadata | No |
| Absent AI content | A 1.4 report whose `ai_enrichment.status` is `not_requested`, `unavailable`, `denied` or `failed`, or a 1.5 report with no completed attempt | "AI analysis not available for this record" (plus the 1.4 status or the attempt reasons) | No |

No retroactive certification: a legacy narrative is never upgraded to a CA-05 analysis, never counted toward workflow completion and never re-labelled. No data deletion: 1.4 reports and their `ai_enrichment` stay readable, read-only, under the 1.4 reader. A user may explicitly request a CA-05 analysis of a historical report only through a separate owner-approved migration/feature; none is planned in the pilot. (At the time of writing no implementation has produced `ai_enrichment` content; the rule exists so later records cannot be misread.)

## 9. Architecture and data summary

```text
Assessment coordinator ──evidence report finalised──▶ Analysis coordinator
Analysis coordinator → Evidence snapshot builder (reads the report + coverage ledger; excerpts via Redaction/source preparation)
                     → Permission evaluator (model_transmission, inference scope) ──pending──▶ UI approval dialog
                     → Model adapter (shared with chat) → Network policy gateway → OpenRouter → downstream model
                     → Response/citation validator → Persistence writer (attempt record, run log manifest)
                     → Combined report generator → typed events → UI
RAG coordinator → may read the authoritative analysis as secondary source (kind ai_analysis); never required
```

| Item (store 1.5 draft) | Change |
|---|---|
| `AnalysisFile` (new root) | One immutable record per attempt: `record_id`, `analysis_id`, `analysis_version`, `attempt_seq`, `supersedes_analysis_id`, `trigger`, report references, terminal status/reason, idempotency key, snapshot manifest (eligible/included counts, exclusions), `ai_evidence_coverage`, disclosure scope, provider/model, versions, `provider_requests[]` (≤ 4), usage, validation, content (null unless completed); path `analysis/<utc>_<repo-slug>_<run-id>_a<version>-t<attempt>.json` |
| `RunSummary` | `analyses[]` (`AnalysisManifest` per logical analysis with its attempt references and `completed_record_id`) and `completion` |
| `ReportFile` | `ai_enrichment` removed (evidence report carries no AI content) |
| `ReportManifest` | `export_revision`, `analysis_id`, `analysis_record_id`, `analysis_version`, `analysis_status_at_render` |
| `SourceRef.kind` | `ai_analysis` |
| `Config` | `analysis` (`AnalysisSettings`, O-AN-2 fields) |
| App contract 1.2 | `ReanalyseReport`, `CancelAnalysis`; `AnalysisStateChanged`, `AnalysisFinished`; `GenerateReportNarrative` withdrawn |
| UI schema 1.2 | analysis tab; status-bar analysis/completion fields; separate scanner-coverage and AI-evidence-coverage labels |

Backward compatibility: no 1.4 record is relabelled 1.5; §8 governs presentation; any data migration needs a separate owner approval and is not run by this change.
