## Findings

1. `Repository.default_ref_kind` and `default_ref_value` are required and non-null in `workbench/crates/domain/src/store/repository.rs` and `schemas/workbench-store-v1.4.schema.json`. The approved CA-06 design requires paired nullable values for the unresolved state and nullable `last_git_version`; a shape change and a new store version are required. Existing `RepositoryFile` and semantic rules must change as well. The design was approved, not its implementation.
2. CA-05's unimplemented draft also calls its global store version 1.5 and changes other root shapes. The versions cannot describe two different contracts. The CA-05 direction was accepted with qualifications, but its contract implementation and any data migration were not authorized (`planning/CA-05-automatic-evidence-analysis.md` §§8–10; `05_Database_Data_Schema.md` §§19, 26).
3. The current reader (`workbench/crates/persistence/src/read.rs`) gates roots to the single `STORE_SCHEMA_VERSION`; the domain `SchemaVersion` serializes/deserializes only the same version and the validator pins the 1.4 schema. No 1.4 historical reader, mixed-version writer or version migration implementation is established by this review. Changing the constant alone would reject old records and is unsafe. Old binaries reject unknown newer versions.
4. `AppCommand` already has add, refresh and remove; repository lifecycle events and `RepoOperation` support clone and update. Those existing shapes do not by themselves establish an identifiable discovery event. The `ApprovalRequested` event does not carry operation name or the target ref; `RepoOperation` has no discovery variant (`workbench/crates/domain/src/contract.rs`). Whether an existing user-visible status/approval flow can expose a safely rendered target without a contract change is unproven.
5. P03 fingerprints bind capability, operation, arguments, repository IDs, destinations, constraints and requested data; the purpose text is not a fingerprint field (`workbench/crates/application/src/permission/fingerprint.rs`). Argument values are hashed, not persisted as cleartext; the unsalted digest can confirm guesses, so syntactic URL validation alone is not a guarantee that paths contain no secrets (`permission/mod.rs`). `ApprovalService::authorise` persists consumption of a once grant before returning proof; a failed write yields no proof. A pending request is never authorization.

## Proposed two-stage request contract

Under the application lock followed by the checkout lock, re-read and validate the repository and remote. For an unresolved reference, propose a `GitAcquire` request with operation `git.discover_default_ref` and exactly one normalized `remote` argument; bind `repo_ids = [id]`, the normalized destination, `repository_metadata`, the approved fixed purpose and a once lifetime, with no workflow/run/inference scope or extra constraints. Only `ApprovalService::authorise` proof permits the discovery call. `NeedsApproval`, refusal, or failed consumption produces no network operation.

Accept only a validated symbolic branch HEAD. Missing, unborn, malformed or unsupported HEAD fails closed and leaves the ref unresolved. Persist a validated ref pair with the checkout still not cloned; after interruption, re-read state and revalidate under locks. For checkout, form a separate `GitAcquire` request with operation `git.clone` and normalized `remote`, `ref_kind` and `ref_value` arguments, and the same repository/destination/data boundaries. Require a fresh authorization of this resolved target before checkout. `git.update` uses `GitUpdate` and the resolved identity. Recheck identity and state immediately before use. Distinct operations and arguments make the discovery grant ineligible for the target operation; never restore a consumed grant after failure. Changed remote/ref requires a matching fresh decision; existing P03 denial precedence still applies, so do not promise automatic reprompt after denial.

**User-visible scope:** the owner approved exploring an existing user-visible flow first; if it cannot safely support the requirement, prepare a versioned contract amendment for review. Current `ApprovalRequested`, `Approval`, and CLI approval output omit operation and ref; they cannot currently present the target associated with a pending approval. `approvals approve <id>` also resolves an ID without reconstructing the target. A fixed purpose alone does not bind or display it.

Inspection found the current typed event, serialized approval view and ID-only decision path insufficient for a cross-client guarantee. The owner approved the versioned amendment in `planning/P04-T03-approval-amendment.md` as T03 contract direction: persisted typed context, fingerprint-checked target presentation and a decision token rechecked under locks. It is not yet a canonical contract change and does not prove implementation feasibility. If reconstruction fails, the request must be stale/unverifiable and cannot be approved. Do not claim informed target approval until the contract is implemented with its tests.

## Required verification for subsequent implementation

- Version dispatch: current, older and unknown newer roots; valid/invalid source; no silent upgrade or loss of historical reports; interrupted writes, backups and recovery; old-binary behavior.
- CA-06 repository: existing refs preserved; both-null and both-valid pairs accepted; mismatched or absent fields rejected according to the approved schema; bounded Git-version grammar and success/failure persistence.
- Authorizations: two separate pending/approve/consume cycles; no Git on pending, denial, or failed persistence; changed remote/ref, stale state, restart and fault injection; malicious/missing/unborn HEAD; no secret/raw repository text in events or logs.
- User-visible approval: the displayed target corresponds to the exact validated fingerprint-bound target, distinguishes discovery, and cannot be spoofed by remote text. Resolve this before claiming the two-stage flow complete.
- E12 per-repository lock layout is noted in Architecture §11 and Data Schema §2; acquire `.app.lock` first, then the checkout lock. Hostile path, mount and same-user race limitations still require the planned P04 fixtures.
