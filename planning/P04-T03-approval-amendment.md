# P04-T03 — proposed versioned Git approval presentation amendment

Status: owner approved this amendment as the T03 contract direction; it is not an applied canonical contract or implementation. The owner approved investigating an existing presentation first. Inspection of `ApprovalRequested`, the persisted `Approval`, CLI `ApprovalRecord`, and `approvals::resolve` shows that the current cross-client contract cannot present and verify the bound Git target: only the fingerprint is durable, the event/view omits the operation and ref, and resolve accepts an ID without an expected target. A CLI-only rendering would not establish the same guarantee for other clients. The owner approved CA-06 store 1.5 then future CA-05 store 1.6; this amendment adds an approval change to the planned CA-06 1.5 scope and proposes app contract 1.2. Since the unimplemented CA-05 draft also proposes app 1.2, its future app version must be rebased (proposed 1.3) in its separately authorized contract task. UI contract version and client migration must be assessed there; do not assume 1.2 or 1.3 already exists.

## Contract proposed

1. Add a nullable typed `git_approval_context` to the persisted `Approval` in the **same CA-06 store 1.5 amendment**, defaulting to null only through a separately authorized, validated migration of existing 1.4 records. Non-Git and historical approvals have null; no historical scope is invented. The P04 variants are `discover` and `target`: both contain the `repo_id` and an application-authored stage; `target` additionally contains validated `ref_kind` and `ref_value`. Values are bounded by the approved Git reference grammar. Do not store the full raw remote or arbitrary Git output. Stored values are sensitive untrusted input and must pass the existing privacy/redaction policy; if a truthful exact display is unsafe, fail closed instead of presenting a misleading redacted target as exact.
2. The application creates the context from the **same validated immutable request snapshot** used to build the existing P03 fingerprint. Store the context and fingerprint in the same pending-record write. On read and before decisions, validate stage, capability, repo ID, destination, state and operation against a freshly reconstructed request from the repository record under `.app.lock`, followed by the per-repository lock. Recompute the P03 fingerprint and require equality to the stored fingerprint. The destination and current repository's full normalized remote remain part of reconstruction; if the repo is absent, changed, unsafe, ambiguous or cannot reconstruct exactly, mark the request stale/unverifiable and refuse approval. Never infer a matching target from the digest alone.
3. Extend the typed `ApprovalRequested` event and approval detail/list response with a bounded, validated, safely displayed Git context and an opaque **review token**. The token must bind the approval ID, stage and exact operation fingerprint; use a versioned domain-separated digest over the canonical values, not a credential or secret. It is a comparison token, not an authentication token. Exact display must distinguish discovery from checkout/update, show repository identity, destination and target kind/value, and preserve the user-visible representation without control-character or bidirectional spoofing. If existing sanitisation or redaction cannot preserve the exact validated target safely, refuse the request. JSON and terminal views use the same typed values; clients cannot treat absent, stale or unverifiable context as valid approval scope. Application-rendered fixed labels separate remote-provided text from decisions.
4. Extend the typed approval decision command/API for **Git approvals** to require the review token returned by the detail view. Under both locks, re-read the pending record and repository; rebuild the operation and target, validate all data and compare both fingerprint and supplied token immediately before persisting the decision. If any check fails, return a typed stale/unverifiable error and do not grant. Existing ID-only Git approve calls must fail closed; non-Git approval behavior remains unchanged. Denial/revocation remains available without presenting a target. Client presentation and decision must be linked to the same approval ID and review token. A client capable of issuing a Git approval must display the returned context before asking for the decision; a machine client explicitly supplies the same token after inspecting structured output. This control cannot prove what a malicious client actually showed a person; client compliance is part of the interface contract.
5. Discovery uses `git.discover_default_ref`, `GitAcquire`, and the validated remote argument; after a consumed discovery grant, only a valid branch symbolic HEAD may be persisted, with checkout still not cloned. The target request uses `git.clone`, `GitAcquire`, and the exact normalized `remote`, `ref_kind` and `ref_value` arguments. Update uses `git.update`, `GitUpdate` and the same identity fields. These operation names and distinct fingerprints do not replace the two separate once authorizations. A validated ref change or remote change requires a newly matched pending request; existing denial precedence still applies. `authorise` consumes each once grant durably before the operation; no grant is restored after failure.
6. Keep `RepoOperation` as clone/update for the enclosing lifecycle unless the implementation needs separate discovery lifecycle events. The new typed approval stage distinguishes the authorization stages; do not emit a discovery-success event that pretends clone succeeded. If client workflows require a separate repository status event, propose and version that addition rather than silently reusing `Clone` to claim completion.

## T03 detailed contract draft

The owner approved this detailed T03 draft for the target contract. It does not change current production types or authorize later implementation or data migration. JSON object examples omit unchanged fields. All new objects reject unknown fields. All fields described as required must be present even when null; missing and null are distinct. UTF-8 byte limits apply before serialization; schema length checks alone count characters and therefore do not replace byte checks.

### Versions and repository fields

- Store 1.5 is CA-06. Every newly written 1.5 store root has `schema_version: "1.5"`; its schema is a new `schemas/workbench-store-v1.5.schema.json`, preserving the 1.4 schema. The application event/command contract is proposed as 1.2. Existing UI contract stays 1.1 only if the exact declarative UI schema is unchanged; otherwise version its schema explicitly before use. CLI JSON gains the fields below; consumers must tolerate a new contract version or use a versioned response. Future CA-05 store 1.6 and app 1.3 are reserved directions, not implemented contracts; CA-05 must separately reconcile its draft and UI version.
- In 1.5 `Repository`, `default_ref_kind` and `default_ref_value` remain required properties but are nullable together: either both null or both non-null. Kind is `branch`, `tag`, or `commit`. A branch/tag value passes the existing `GitRefName` validator (1–255 UTF-8 bytes) and the additional Git ref checks in the approved T01 procedures; a commit value is a full lowercase 40- or 64-hex `GitOid`, not an arbitrary revision expression. Branch discovery records the branch value in the same canonical representation used in the fingerprint and subsequent fetch; do not mix `refs/heads/x` and `x` without one documented conversion. Schema `oneOf` enforces both-null/both-non-null and semantic validation enforces kind-specific grammar. Since the current Rust field uses `GitRefName` for all kinds, implementation needs a kind-aware validated representation or equivalent explicit validation.
- Compatibility qualification: existing 1.4 records may contain refs accepted by the old `GitRefName` parser (including `HEAD`) that fail the narrower P04 operation rules. Never rewrite such a value into a guessed branch or silently drop it. If a valid 1.4 repository cannot satisfy the proposed 1.5 kind-specific rule, stop its migration and report a typed manual-decision requirement; preserve the original and backup. No migration should start publishing roots until the complete preflight has identified this case. Approval of the high-level direction does not decide how to convert such a record.
- Add required nullable `last_git_version`: null or canonical numeric `2.53.PATCH`, where PATCH is ASCII `0` or a non-zero digit followed by at most five digits, no leading zero, no suffix and maximum 11 bytes. This is the persisted value parsed from a successful allowlisted version probe, not raw `git --version` output; unrecognized suffixes or versions outside the allowlist fail closed rather than being truncated. Only a verified successful Git acquire/update writes it together with commit OID and timestamp; failures retain the last successful tuple. Widening the allowlist or version grammar requires the applicable future qualification.

### Persisted approval context

Add required nullable `git_approval_context` to each 1.5 `Approval`. Null is valid for non-Git and migrated historical approvals; null on a Git approval is **not** sufficient to approve or execute it. Non-null is exactly one of:

```json
{"stage":"discover","repo_id":"<uuid>","ref_kind":null,"ref_value":null}
{"stage":"clone","repo_id":"<uuid>","ref_kind":"branch","ref_value":"<validated ref>"}
{"stage":"update","repo_id":"<uuid>","ref_kind":"branch","ref_value":"<validated ref>"}
```

For `clone` and `update`, `ref_kind` is one of `branch`, `tag`, `commit` and `ref_value` obeys the kind-specific rule above; the examples are not an exhaustive enum of kind values. `discover` requires both ref fields null, exactly one repo ID in the approval matching `repo_id`, `git_acquire`, no workflow/run/inference binding, once lifetime and one normalized destination. `clone` has the same constraints plus `git_acquire`; `update` has `git_update`. Other stage/capability/scope combinations, absent fields, extra properties and mixed-null pairs fail semantic validation. Historical null-context Git approvals cannot be approved or used for a P04 operation; create a new matching pending request subject to the existing denial rules. Do not reinterpret or delete old records automatically.

### Request, view and decision

The operation/arguments are exact: `discover` = `git.discover_default_ref` with one `remote` argument; `clone` = `git.clone` and `update` = `git.update`, each with `remote`, `ref_kind`, `ref_value`. `remote` is the full normalized credential-free remote including applicable SSH user, port and path; fingerprint v1 is unchanged. Each request has one repo ID, one normalized destination, `repository_metadata`, fixed application-authored purpose, no workflow/run/inference scope, no resource constraints, once lifetime and no validity bound. Arguments have unique names. Failure to construct or safely display the exact remote/ref fails closed; do not write raw Git output, raw secrets or arbitrary helper output to an event/store.

Extend `ApprovalRequested` and the application approval detail DTO with required `git_approval_review`, null for non-Git or unverifiable records, otherwise the exact object below. In a list, include the same nullable field; a dedicated `approvals show <id>` returns one detail. `operation` is one of the three literal operation names above. `remote_display` is a redacted-safe, single-line rendering of the exact normalized remote **only if it preserves its entire identity**; the corresponding repo identity and normalized destination must also be shown. A remote or ref that cannot be shown without secret disclosure or ambiguity is refused; never silently mask a meaningful substring and still call the scope exact. Ref and remote for a valid review are restricted to printable ASCII bytes 0x21–0x7e; escape `\\` and `"` in human and JSON rendering with normal JSON string escaping, and use labeled, quoted fields. No controls, whitespace, bidi controls, Unicode confusables or terminal escape sequences are accepted for these values. This presentation restriction is in addition to existing parsers and may refuse otherwise valid refs; do not claim universal secret detection. Use the project's approved redaction policy, and fail closed when it flags or cannot safely classify the value. `remote_display` and `ref_value` are transient reviewed view fields, not extra persisted raw remote or raw process output.

```json
{"stage":"clone","repo_id":"<uuid>","operation":"git.clone","remote_display":"<exact safe normalized remote>","destination":"<normalized destination>","ref_kind":"branch","ref_value":"<exact safe ref>","review_token":"<64 lowercase hex>"}
```

For `discover`, `ref_kind` and `ref_value` are null; for `clone`/`update` they are non-null. Stage, operation, capability and refs must agree with the persisted context. Add `review_status` to the detail/list DTO: `not_applicable`, `ready`, or `stale`; `git_approval_review` is non-null exactly for `ready`. `ApprovalRequested` carries a review object only after the same verification, or null with `review_status: "stale"`; never emit a guessed target. An event is a snapshot, so clients refresh detail before decision. `approvals list --json` and `approvals show --json` expose the same typed fields and `app_contract_version: "1.2"`; human output labels stage, repository, remote, destination, ref kind/value and token. TUI/client adapters consume the same application DTO. `ResolveApproval` gains a required nullable `review_token` field in app contract 1.2; `approvals approve <id> --review-token <token>` supplies it. Git `approve_once` without a valid token, Git workflow-scope approval, stale context, or a null/missing context fails closed. Deny and revoke remain possible without a token; non-Git decisions require null and preserve their existing behavior.

Review token v1 is lowercase hex SHA-256 over `b"pwt-git-approval-review\0v1\0" || ascii(canonical-lowercase-uuid) || b"\0" || ascii(stage) || b"\0" || ascii(operation_fingerprint_lowercase_hex)`. No trailing delimiter. The stored fingerprint is the P03 v1 digest recomputed from reconstructed request data. Token is deterministic, not secret, not proof of display, not an authentication mechanism, and is not stored as a separate authority. Token reuse for the same still-pending unchanged record is allowed; use after decision fails because state is no longer pending. At decision time, under `.app.lock` then `checkouts/.locks/<repo-id>.lock`, load pending approval and repository, verify state, context, current remote/ref/destination, fixed stage mapping and fingerprint; compute token and compare against the supplied 64-hex value. Any missing/mismatch/refusal or persistence error leaves no grant. Client display occurs before the decision; the recheck prevents stale-state approval but cannot prove what a malicious client displayed.

Token encoding test vector: ID `00000000-0000-4000-8000-000000000001`, stage `clone`, fingerprint 64 ASCII zeroes produces `c678c484d79f9d50efd0442ee3ae552e1eefd83653fa109c821c829c45fa99f1` (SHA-256); it checks framing only, not request validity. Existing `Authorisation` is not itself type-bound to the request: after `authorise`, revalidate and execute the exact request in the same locked service control flow; do not cache, persist, reuse or expose its proof as a generic capability. Across prompts release and later reacquire both locks and reconstruct from persisted state. A pending-record write can succeed while event emission fails: recovery must list/reuse that existing pending record, not claim rollback or silently create a duplicate; the detail lookup remains available. Interrupted discovery leaves the ref unresolved unless the validated pair was durably written, and never marks checkout ready.

### Version transition and failure handling

The existing 1.4 reader/writer is single-version. The future migration must first provide a tested 1.4 validator/reader and version dispatch; unknown newer roots fail closed. Under `.app.lock`, inventory and validate every existing operational root and references, make recoverable copies, construct candidate 1.5 roots, validate all candidates, then use a durable migration journal with an explicit prepare/commit marker and per-file hashes so interruption recovery completes or restores the entire set before normal writes resume. An ordinary per-file atomic rename is not a cross-root transaction; never claim otherwise. The exact journal storage and fsync semantics must be designed and tested before any real migration, and a missing, invalid or ambiguous journal must stop writes. Data conversion requires separate owner authorization.

For `repo.json`, preserve all 1.4 values including both valid reference fields and append `last_git_version: null`; for `approvals.json`, preserve all existing approval fields and append `git_approval_context: null` to each record. The eight writable operational kinds are Config, Repositories, Workflows, Approvals, Log, RagIndex, Conversations and ToolManifest; the six other than Repositories and Approvals retain their 1.4 shapes apart from the version. Convert only present roots after validation and explicitly prove every root's semantic equivalence; absent optional files stay absent. Suppressions is reserved/read-only and stays under its original reader. Immutable reports and backups stay byte-for-byte 1.4 and are served by a tested 1.4 read-only reader. Old binaries reject 1.5; rollback after any 1.5 write requires the pre-migration backup and explicit recovery, never silent downgrade. The writer's single `.prev` generation is not a durable migration backup. CA-05's later 1.6 contract must define its own transition and preserve both 1.4 and 1.5 historical report readers without invented analysis data. No migration is executed by T03.
