## Anomaly (observed by the D07 worker: 2 failures in 6 `cli` runs; lead: 0 in 6 — intermittent)
`cli/tests/p02_scenarios.rs::lock_held_by_another_holder_exits_3` (~line 772): after `drop(held)`, the immediate `store validate` sometimes exits 3 instead of 0 (assert at ~line 796).

**Lead diagnosis (hypothesis, consistent with POSIX `flock` semantics; not yet reproduced deterministically):** the test holds the data-directory lock through an open file description in the *test process*. Sibling tests in the same test binary run in parallel threads and spawn the CLI (`Command::new(BIN)`); each spawn duplicates the test process's file table until `exec` closes `O_CLOEXEC` descriptors. A `flock` is released only when every descriptor of the open file description is closed, so for that short fork→exec window the lock survives `drop(held)`, and a CLI started in that window sees it held. The product is not affected (the CLI does not spawn processes while holding the lock); the race is in the test's post-release assertion.
