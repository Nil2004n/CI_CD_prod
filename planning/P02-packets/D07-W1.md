## Confirmed defect (lead diagnosis)
`persistence/src/atomic.rs` `replace_steps` with `keep_previous`: after a failure at `WriteStep::Replace`, `<name>.prev` already names the same inode as `<name>` (the `.prev` rename succeeded, the main rename did not). On the next successful rewrite the code hard-links `<name>` to `.<name>.prev.tmp-<hex>` and renames that over `<name>.prev`; POSIX `rename(2)` between two links of one inode succeeds **without doing anything**, so the temp name stays; `temps.forget(&prev_tmp)` then drops it from cleanup. Effect: a successful write leaves a stray temp (removed only by the next `recover`). Reproduction: `application/tests/dev_store_faults.rs::f1_a_rewrite_after_a_failed_replace_leaves_no_stray_prev_temp` (currently `#[ignore]`).

## Bounded fix (do exactly this; anything else → STOP and report)
1. `persistence/src/atomic.rs`, `replace_steps` only: after the `ReplacePrevious` rename succeeds, if `prev_tmp` still exists (`fs.symlink_metadata(&prev_tmp)` is `Ok`), remove it with `fs.remove_file(&prev_tmp)`; a removal error (or a metadata error other than `NotFound`) is returned as a storage error attributed to `WriteStep::ReplacePrevious` **before** the main `Replace` (target still untouched, as the protocol requires); keep `prev_tmp` registered in `temps` until it is gone so the error path still cleans it. Rustdoc/comment: why (POSIX no-op rename of two links of one inode). No other behaviour change.
